# Paid AI: disabled until existing identity and durable admission are configured

## Current state

No existing identity application, production PostgreSQL store, live provider credential or account authorization was established in this task. `PAID_AI_ENABLED` defaults off and vercel.json explicitly sets it to `0`. Setting GOOGLE_API_KEY alone cannot expose a paid route. The public page, code editor, sanitizer, session history, clipboard, SVG download and local PNG conversion require neither a caller identity nor provider configuration. All existing AI controls remain, but paid actions report an actionable closed response until configured and authorized. History entries are native buttons supporting Tab, Enter and Space in the retained row layout.

This is an adapter for **pre-existing** RS256 OIDC identity, not a new identity service/login/enrollment integration. It supports a verified bearer JWT from an existing identity gateway/client, or a Cloudflare Access application assertion forwarded by an **already established** gateway. No identity/database/key/domain resource was provisioned and no production authorization/account setting changed. If those existing resources are unavailable, hosted paid mode must stay disabled.

## Authorization contract

`paid_access.py` guards all four application-owned-key paths: /generate, /analyze_image, /convert_to_svg and /refine_svg. No per-process bypass, origin trust, CORS rule, asserted email, X-User header or client-supplied quota principal is used as authorization. Identity requires RS256 signature verification against operator-pinned public JWKS, exact HTTPS issuer and audience, exp/iat validation (maximum one-hour lifetime), and an explicit allowlist of stable subject IDs. Unknown keys, algorithms, subjects, missing/expired assertions or invalid trust configuration fail closed. Caller jku/x5u/key headers are never fetched. Database counters use a hash of verified issuer plus subject, not attacker-selected headers. Valid identities outside the allowlist receive 403. Missing/invalid identities receive 401. Disabled, stale or incomplete policy/storage configuration receives 503; quota denial receives 429; deadline denial receives 504.

Public JWKS are trust anchors, not secrets. Pin them from the administrator-verified existing issuer, never from a token's unverified issuer/header URL. Rotation/revocation requires the owner to refresh keys and the shared policy fingerprint. A policy expires within at most 24 hours, forcing re-review/refresh of signing trust, model limits and price ceilings; it cannot remain silently enabled indefinitely. There is no automatic key enrollment or identity resource provisioning.

References: [Cloudflare token validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/), [application assertions](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/). Header presence alone is never sufficient.

## Durable admission and failure behavior

Production requires an **existing external PostgreSQL primary**, appropriate to the repository's intended Vercel/serverless host. `sslmode=verify-full` and normal CA/hostname verification are mandatory. There is no SQLite, Vercel filesystem or in-memory quota fallback. The application never creates/enrolls its own schema or initializes a production policy fingerprint.

`sql/paid_admission.sql` defines a global guard row, UTC daily/minute budget buckets and per-attempt admission records. A transaction locks the guard row across all workers/processes, verifies the exact policy fingerprint, then atomically charges global, per-principal and per-model daily request limits, global/per-principal minute limits, token/cost budgets and global/per-principal in-flight limits. PostgreSQL's clock defines quota windows and stored deadlines. Partial charges roll back on any denial. Counters are independent of process memory and persist through application restarts; policy changes do not reset them.

Supported paid models are restricted to gemini-3.8-flash and gemini-3.5-flash-lite, and the operator must explicitly enable a subset. Each attempt reserves the **entire documented 1,048,576-token input envelope plus 65,536-token output/thinking envelope**, even if the configured output cap is lower and the actual prompt is tiny. This deliberately over-reserves text and image usage without a paid token-count call or trusting usage reports. Model references: [3.8 Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash), [3.5 Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite). Per-action SDK output is additionally capped at 8192 and the reviewed policy may lower it. No provider tools, retries or auxiliary paid calls are enabled.

Cost admission is integer micro-USD: full input envelope × reviewed maximum input micro-USD/token plus full output envelope × reviewed maximum output micro-USD/token. Fractional micro-USD prices must be rounded **up**. The application enforces at most $100 global/$20 principal per UTC day in these conservative admission units, with lower policy values allowed. This is not a guarantee against provider price changes, taxes or an incorrectly configured price ceiling. Owners must verify highest applicable price tiers/limits and any existing provider-account hard spending controls before enabling. Token/request/cost reservations are never refunded, including provider failures, timeouts, disconnects and crashes.

In-flight slots do **not** expire/release merely because a deadline passes. A crashed/uncertain provider attempt keeps its slot indefinitely, across restarts, until an operator reconciles its outcome against provider evidence. Provider exceptions mark uncertainty; cleanup/storage failure leaves the slot occupied. A known returned response releases its slot, but late responses are discarded. Never clear uncertainty based solely on wall time or allow clients to reset quotas. This sacrifices availability rather than permit deadline/restart cost bypass. Some uncertain outcomes may not be provably reconcilable; in that case leave paid mode disabled and the reservation intact.

Admission time is bounded: database connect 3 seconds, statement 2 seconds, lock wait 1 second; per-request deadline at most 20 seconds including authorization/input processing/admission. The SDK receives the remaining HTTP timeout and one attempt. HTTP library timeouts cannot prove remote computation cancellation or a hard process wall-clock stop. Durable reservations/uncertain slots are the protection in that case, not a claim that timeout makes a remote paid call disappear.

## Exact human setup for existing resources only

1. Keep vercel.json's `PAID_AI_ENABLED=0` and do not deploy this task. Confirm the existing issuer, application audience and stable subject IDs from the identity administrator's records. Confirm that the existing gateway/client already authenticates intended users and forwards a signed assertion for these paths. This slice supplies no login redirect, new app registration or frontend token storage. If no such existing application exists, stop here; do not create one under this task.
2. Obtain that existing issuer's **public** signing JWKS through its verified HTTPS metadata/admin documentation. Confirm RS256, key IDs and 2048-bit-or-stronger RSA keys. Review allowlisted subjects and session lifetime ≤1 hour. Select exactly one assertion source: `authorization` for `Authorization: Bearer ...`, or `cf-access-jwt-assertion` for an already established Access gateway. Never map unverified email/headers to subject IDs. The origin still validates the JWT, including direct-origin requests.
3. Have the database owner apply sql/paid_admission.sql to an **existing** durable PostgreSQL database using its existing migration authority. Do not provision a database/user/password here. Use a separate existing application role with SELECT on the guard, UPDATE(id) permission needed for FOR UPDATE, SELECT/INSERT/UPDATE on budget/admission tables, and no DDL, DELETE/TRUNCATE or policy_hash-update rights. Protect its schema/search path from untrusted writers. Use the existing primary/pool endpoint with certificate-verified TLS and no lossy replica/ephemeral storage. Recovery/rollback can invalidate admission history: keep paid mode off until the owner reconciles restored counters and pending attempts.
4. Review docs/paid-policy.example.json. Its zero expiry/prices are intentionally invalid: **do not enable it as-is**. Set current conservative per-token price ceilings after checking provider pricing, select the allowed low-cost model(s), set all budgets and a valid_until epoch no more than 24 hours ahead. Review the full-context reservation's intentionally low effective request allowance. Refresh/reconcile before expiry; never reset counters to make a new policy pass.
5. Configure only server environment values: PAID_AI_ISSUER, PAID_AI_AUDIENCE, PAID_AI_SUBJECTS (JSON array), PAID_AI_JWKS (public JWKS JSON), PAID_AI_IDENTITY_HEADER, PAID_AI_DATABASE_URL (existing server-only DSN with sslmode=verify-full and appropriate root CA, e.g. sslrootcert=system when supported), PAID_AI_POLICY (reviewed JSON), and the already existing server GOOGLE_API_KEY. Do not copy credentials/cookies from a local machine or put a key/DSN/JWT in browser code. No actual values were supplied in this task.
6. In the owner's isolated configuration context, use `PAID_AI_ENABLED=1 python -m paid_access fingerprint` to print the non-secret policy fingerprint. This command validates configuration but does not connect/provision/call a provider. Using the existing migration authority, insert `(1, '<reviewed fingerprint>')` into paid_ai_guard. Future changes must update that fingerprint under its row lock while retaining all counters/admissions. Mixed old/new workers will fail closed until synchronized.
7. Only after separate owner review and approved rollout, remove/change the checked-in hard-disable and enable PAID_AI_ENABLED=1 in the intended hosted environment. Before any live paid verification, obtain explicit authorization; none is performed here. Confirm invalid/spoofed callers cannot dispatch, direct origin is guarded, and authorized existing identities receive the reviewed quotas. Branch protection, domains, IdP policies and production deployment are outside this task.
